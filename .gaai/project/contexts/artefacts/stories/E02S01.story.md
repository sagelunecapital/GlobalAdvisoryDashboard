# Story E02S01: Fetch and Persist FRED Liquidity Data and Bitcoin Price

## User Story

**As a** fund manager,
**I want** the dashboard to automatically retrieve and store historical and current liquidity indicator data,
**so that** I have a complete, up-to-date dataset ready for display and analysis without manual data collection.

---

## Context

The Liquidity module requires five FRED series and Bitcoin price. Four FRED series are available weekly via the FRED API (WRESBAL, WALCL, WDTGAL, WLRRAL); one is monthly (BOPGSTB). Bitcoin price is available weekly and monthly via Barcharts or Yahoo Finance. History must go back to 2020-01-01. All raw series must be stored before derived computations (net liquidity, YoY%) can be run.

---

## Acceptance Criteria

- [ ] AC1: Given initial setup, the system fetches WRESBAL (Reserve Balances with Federal Reserve Banks) from FRED API with weekly frequency from 2020-01-01 to the most recent available date and persists all records
- [ ] AC2: Given initial setup, the system fetches WALCL (Fed total assets), WDTGAL (deposits at Federal Reserve), and WLRRAL (reverse repurchase agreements) from FRED API with weekly frequency from 2020-01-01 and persists all records — these three are stored as separate series to enable net liquidity computation
- [ ] AC3: Given initial setup, the system fetches BOPGSTB (US trade balance of goods and services) from FRED API with monthly frequency from 2020-01-01 and persists all records
- [ ] AC4: Given initial setup, the system fetches Bitcoin price with weekly and monthly frequency from 2020-01-01 and persists all records — Delivery chooses the data source (Barcharts or Yahoo Finance)
- [ ] AC5: Given a subsequent refresh run, the system fetches only the dates not yet in the database and appends them — historical data is never overwritten or deleted
- [ ] AC6 (error-handling): Given a FRED API call fails for any series, the system surfaces a visible error identifying the specific series that failed — it does not partially persist a subset while silently omitting others, and it does not crash
- [ ] AC7 (error-handling): Given the Bitcoin price source is unavailable, the system surfaces a visible error for that series and continues fetching the FRED series — failures are isolated per source
- [ ] AC8 (data-freshness): Given data is fetched, each stored record includes the series ID, date, value, and the timestamp of the fetch — stale data is never displayed as current

---

## Out of Scope

- Computing derived series (net liquidity, YoY%) — handled in E02S02 and E02S03
- Displaying data — handled in E02S04
- User-configurable series selection

---

## Dependencies

None — first story in E02; establishes the data foundation.

---

## Notes

Delivery has full freedom to choose the persistence layer (SQL, file-based, etc.) as long as it supports append-only operations and the schema accommodates all five FRED series plus Bitcoin. FRED API key required — Delivery must document how to configure it. Bitcoin source (Barcharts or Yahoo Finance) is Delivery's choice; prefer a source with a stable programmatic API. BOPGSTB is released monthly by the BEA and published to FRED with a lag of approximately 5 weeks — Delivery should note this lag in the data freshness display.

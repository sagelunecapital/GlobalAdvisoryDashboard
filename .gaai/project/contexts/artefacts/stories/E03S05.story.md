# Story E03S05: Refresh Macro Indicator Data

## User Story

**As a** fund manager,
**I want** to refresh the macro indicator data on demand,
**so that** the dashboard reflects the latest released values and updated signal states without requiring a full re-initialization.

---

## Context

Macro indicators are released on varying schedules (weekly for yields and currencies, monthly for inflation and growth). A refresh operation fetches only new observations since the last stored record per indicator, recomputes % change, rolling std dev, and signal detection for the new observations, and updates the display. The operation must be incremental and idempotent.

---

## Acceptance Criteria

- [ ] AC1: Given a refresh is triggered, the system fetches only new observations (postdating the most recent stored record) for each of the 32 indicators — no full historical re-fetch occurs
- [ ] AC2: Given new raw data is fetched for one or more indicators, the system invokes the % change, rolling std dev, rolling mean, and signal detection pipeline for the new observations — recomputing and updating derived metrics and signal state for the refreshed indicators
- [ ] AC3: Given the refresh completes successfully, the display reflects the newly available data and recomputed signal states — either via automatic UI update or on the next manual page refresh; no full re-initialization is required
- [ ] AC4: Given a refresh is triggered and no new data is available for any indicator (all series are at their most recent release), the system completes with no data changes and surfaces a confirmation message indicating the data is current — no error is raised
- [ ] AC5 (error-handling): Given one or more indicators fail to update during a refresh, the system surfaces a visible error identifying the failed indicators — successfully updated indicators are stored and displayed; the failure does not roll back the full refresh
- [ ] AC6 (data-freshness): After each successful refresh, the display date stamp for the module is updated to reflect the new most-recent fetch timestamp
- [ ] AC7 (signal-detection): Given a refresh produces a new observation whose z-score crosses the 2σ threshold (z ≥ 2 or z ≤ −2), the signal detection pipeline generates a new signal record for that indicator and sets its is_current flag — stale signal state from prior refresh runs does not carry forward as the current signal state for any indicator

---

## Out of Scope

- Automatic scheduled refresh (manual on-demand only; scheduling is a future enhancement)
- Re-fetching or recomputing the full historical series — incremental append only

---

## Dependencies

- E03S01 — data fetch pipeline must exist
- E03S02 — % change and std dev computation must exist
- E03S03 — signal detection must exist
- E03S04 — display must exist to show refreshed data

---

## Notes

Refresh should be implemented as a callable function or script that can later be wired to a scheduler. Running refresh twice in succession with no new releases must produce no data changes and no errors. For monthly indicators, the system should detect whether a new release has occurred since the last stored record — if not, no fetch is needed for that indicator.

# Story E03S02: Compute Weekly % Change and Rolling 52-Week Standard Deviation

## User Story

**As a** fund manager,
**I want** to see each macro indicator's week-over-week change and how far it sits from its recent baseline,
**so that** I can assess the pace and magnitude of macro shifts, not just their raw level.

---

## Context

For each of the 32 indicators, two derived metrics are required: (1) week-over-week % change (or period-over-period % change for monthly indicators), and (2) a 52-week rolling standard deviation and rolling mean of the raw value. These metrics feed the signal detection story (E03S03) and the display story (E03S04). All computation reads from the locally stored series; no external API calls are required.

---

## Acceptance Criteria

- [ ] AC1: Given stored indicator data, the system computes week-over-week % change for each indicator as ((current − prior) / |prior|) × 100 for all available date pairs and persists the result as a named derived series per indicator (e.g., `CPI_YOY_PCT_CHG`)
- [ ] AC2: For monthly-released indicators (CPI, Core CPI, PCE, Core PCE, PPI, ISM Manufacturing, ISM Services, NFP, Unemployment Rate, Retail Sales), % change is computed as period-over-period (most recent release vs. prior release) rather than week-over-week
- [ ] AC3: Given stored indicator data, the system computes a 52-week (52-observation for weekly series; 12-observation for monthly series) rolling standard deviation and rolling mean for each indicator's raw value and persists both as named derived fields per indicator (e.g., `US_10Y_YIELD_STDDEV_52W`, `US_10Y_YIELD_MEAN_52W`)
- [ ] AC4: Given fewer than 52 observations are available for a given indicator, the rolling std dev and mean are computed over the available window (minimum 4 observations) with the actual window size recorded — no computation is skipped due to a partial window
- [ ] AC5: Given a date where the prior value is missing (e.g., first record in the series), that date is excluded from the % change series — no null division is attempted
- [ ] AC6: Given new raw data is appended by E03S01, the system computes % change only for the new observation(s) and appends those values. For rolling std dev and rolling mean, the system recomputes the full trailing 52-week window (or 12-month window for monthly indicators) from stored raw data on each refresh — rolling statistics are not append-only, as adding a new observation changes the window composition and therefore the std dev for the current period
- [ ] AC7 (error-handling): Given a raw series is empty or corrupt for a given indicator, the system logs a warning and skips that indicator's derived computation without blocking the remaining indicators
- [ ] AC8 (data-freshness): Each stored derived record includes the computation timestamp
- [ ] AC9 (signal-detection): Given rolling mean and rolling std dev are computed and stored for an indicator, both values are queryable by series ID and date — stored as separate named fields (e.g., `rolling_mean`, `rolling_std_dev`) — sufficient for E03S03 to compute z = (current_value − rolling_mean) / rolling_std_dev without additional transformation

## Notes

Standard deviation is computed over the raw value (not the % change) to allow E03S03 to compare the current raw value against the 52-week mean ± 2σ. Both rolling mean and rolling std dev are stored per indicator so E03S03 can compute the z-score directly. For spread indicators computed from two yields, std dev is computed on the spread value itself. The trailing-window recompute on refresh is intentional — rolling statistics by definition change when the window advances, so append-only logic would produce stale std dev values.

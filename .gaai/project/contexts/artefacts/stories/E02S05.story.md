# Story E02S05: Refresh Liquidity Data

## User Story

**As a** fund manager,
**I want** to refresh the liquidity data on demand,
**so that** the dashboard reflects the most recently available FRED releases and Bitcoin price without requiring a full re-initialization.

---

## Context

FRED series are updated on a weekly or monthly release schedule. Bitcoin price updates continuously but is captured at weekly or monthly frequency. A refresh operation must fetch only new data points since the last fetch, recompute derived series (net liquidity, YoY%, 3MA) for the new date range, and update the display — without re-downloading or recomputing the full history.

---

## Acceptance Criteria

- [ ] AC1: Given a refresh is triggered, the system fetches only data points for each series that postdate the most recent stored record for that series — no full re-fetch of historical data occurs
- [ ] AC2: Given new raw data is fetched, the system runs E02S02 (net liquidity computation) and E02S03 (YoY% and 3MA computation) for the new date range and appends results to the respective stored series
- [ ] AC3: Given the refresh completes successfully, the display updates to reflect the newly available data — the fund manager does not need to reload the application
- [ ] AC4: Given a refresh is triggered and no new data is available (all series are already at their most recent release), the system completes with no data changes and surfaces a confirmation message indicating the data is current — no error is raised
- [ ] AC5 (error-handling): Given one or more series fail to update during a refresh, the system surfaces a visible error identifying the failed series — it does not silently leave stale data without notification
- [ ] AC6 (data-freshness): After each successful refresh, the display date stamp for each series is updated to reflect the new most-recent data date

---

## Out of Scope

- Automatic scheduled refresh (this story delivers manual on-demand refresh; scheduling is a future enhancement)
- Re-fetching or recomputing historical data — incremental append only

---

## Dependencies

- E02S01 — data fetch pipeline must exist
- E02S02 — net liquidity computation must exist
- E02S03 — YoY% and 3MA computation must exist
- E02S04 — display must exist to show refreshed data

---

## Notes

Delivery should implement refresh as a callable function or script that can later be wired to a scheduler. The refresh operation should be idempotent — running it twice in succession with no new FRED releases should produce no data changes and no errors.
